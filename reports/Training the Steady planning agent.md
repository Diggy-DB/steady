# Train the planner on itself, not Gemini

The best way to make Steady's Qwen3-4B-Thinking-2507 agent more accurate is to fix the agent harness in code first. After that, train the model on its own code-checked successes, then run a short reinforcement-learning pass inside the real tool loop. The Gemini distillation idea should be dropped. The main failure is not a knowledge gap that a teacher can fill. On the RTX 4090, both week_plan runs made **zero proposals even after the nudge**, and the synthetic task generator **has no task type that combines a weekly activity with several assignments**, so no training method can learn that pattern from the current data. Code that counts "remaining goals" for the model, rejects duplicate proposals and forces a proposal on the nudge round attacks those failures for $0. The already-built rejection-sampling session (about $2–5) then teaches the model to propose directly and think less. A 50–100-step multi-turn GRPO run with LoRA on a 48 GB GPU (about $5–12) is the main training lever for the loop and coverage failures. Expect only a single-digit gain from it, because plain GRPO has also made this exact model worse. Gemini fails all three tests the question asks about. Google's terms bar using its output to develop competing models. The API returns only reasoning summaries, which a thinking student cannot learn from, and it cannot score the student's tokens. Apache-2.0 Qwen teachers give full reasoning in the student's exact format for less money. None of these gains will show up on the current 12-trial suite, which can only detect changes of about 40 points. A frozen held-out set of 60–100 scenarios, run three times per variant and compared pairwise, therefore comes first. The whole plan fits in roughly **$15–30 of RunPod time**.

## Five steps, about $15–30, ranked by payoff per dollar

The steps are ordered so that each one makes the next one work. The table gives the plan. Every expected gain in it is an estimate drawn from the evidence in later sections, not a measurement on this agent. Costs use RunPod prices of about **$0.34/hr (Community) to $0.69–0.89/hr (Secure) for an RTX 4090** and **$0.79–0.99/hr for a 48 GB L40S**. Price trackers disagree, so check the live page ([RunPod pricing](https://www.runpod.io/gpu-cloud/pricing); [computeprices 4090](https://computeprices.com/providers/runpod/gpus/rtx4090); [computeprices L40S](https://computeprices.com/providers/runpod/gpus/l40s)).

The harness comes first because training data is collected through it. If you train an adapter (the small LoRA add-on weights) and then change what the tools return, the adapter was trained on an interface it no longer sees. Harness fixes also lift the hardest tasks from "never passes" to "sometimes passes". Rejection sampling needs that, because it keeps only passes. GRPO needs it too, because a group where every try passes, or every try fails, carries no learning signal. Self-RFT comes before GRPO for two reasons. It shortens thinking, which cuts the cost of every RL rollout roughly in proportion, and it gives RL an on-distribution starting point. That ordering is inference, not something a study has tested. The one-script RunPod session that hasn't been run yet is still worth running now, as a $2 end-to-end shakeout of collect, train and eval. Read its 6-scenario comparison as a smoke test, not a verdict. Steps 0–3 total roughly $10–25, which leaves room for step 4 or a rerun.

## Week_plan breaks in the interface and the data, not the weights

The RTX 4090 logs show what training is up against. Both week_plan runs ended with **zero proposals**: 0 of 2 new gym sessions and 0 of 180 minutes for each assignment. Both runs had received the nudge, and one ended with an empty answer. One due_tonight run failed by using up all **8 rounds**, and the nudge fired in **6 of 12 runs** ([week_plan log](../ai/evals/2026-11-05-1846-Qwen_Qwen3-4B-Thinking-2507-gpu-4090-week_plan.jsonl); [due_tonight log](../ai/evals/2026-11-05-1846-Qwen_Qwen3-4B-Thinking-2507-gpu-4090-due_tonight.jsonl)).

The training data has a matching hole. The generator's six task types include weekly_goal ("gym twice this week", minus sessions already scheduled) and task_time (time for one assignment), but no type combines them. Week_plan asks for gym three times, with one session already on Tuesday, plus three hours each for two assignments ([synth.py](../ai/src/ai/synth.py); [evals.py](../ai/src/ai/evals.py)). So rejection sampling, GRPO and any teacher would all train on data that lacks the failing pattern. Every training step therefore needs a **`multi_goal` task type** first: one activity count plus one to three assignments, with existing events to subtract. Its phrasing templates must differ from week_plan's so the eval stays held out.

The cheapest well-supported lever is interface design. Anthropic advises building "a few thoughtful tools targeting specific high-impact workflows". Its example is a `schedule_event` tool that "finds availability and schedules an event". It also recommends error messages that give "specific and actionable improvements" ([Anthropic, writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). SWE-agent's ablations show interface design alone moving success by several points on an 18.0% base. Removing the linting guardrail cost **3.0 points**, and replacing summarized search with step-by-step search cost **6.0** ([SWE-agent](https://arxiv.org/html/2405.15793)).

For Steady, this means letting code do the counting the 4B gets wrong. One option is to append a code-computed goal-status line to every tool result, for example "gym: need 3, already 1 (Tue 6–7 PM), pending 1, remaining 1". The other is a read-only `check_plan(goals=[...])` tool. The model states the goals once, and code returns, for each goal, the existing matches, pending proposals, remaining count and candidate slots. A read-only tool keeps the propose-only rule intact. The `propose_new_event` and `propose_move_event` tools also need guardrails. They should reject a duplicate or already-pending move with an actionable message. Once the remaining count hits zero, they should reply "All requested items are proposed; reply to the user now", which targets the due_tonight round-cap failure. This evidence comes from frontier models, so the effect on a 4B is unmeasured. But the failure is bookkeeping, and code does bookkeeping reliably.

vLLM (the inference server on the pod) has two controls aimed at the remaining failures. The first is named or `required` tool choice, which uses constrained decoding. The docs promise "a validly-parsable function call - not a high-quality one" ([vLLM tool calling](https://docs.vllm.ai/en/latest/features/tool_calling.html)). Apply it **only on the nudge round**, never globally, since the agent must end with a text reply. That turns "described times but proposed nothing" into a well-formed proposal, which the existing validators then check. The vLLM docs are ambiguous about whether constrained output suppresses the thinking before it, so test one nudge request before relying on it.

The second control is the per-request `thinking_token_budget`, which forces `</think>` once the budget is reached ([vLLM reasoning outputs](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html)). That caps latency and makes the new unclosed-thinking salvage a rare path rather than a routine one. Sweep 2k, 4k, 8k and unlimited on the held-out set. A reasonable start is 4–8k for the planning turn and 1–2k for follow-up rounds, but forced truncation can cut a plan off mid-count, so let the sweep decide. Also set `strict: true` on the four tool schemas if the pod's vLLM version supports it alongside the hermes parser. These controls exist only in vLLM. Ollama's equivalents were not checked, so the Mac path should rely on the code fixes.

Running several tries and keeping one that passes a code check is the one inference-time lever with strong evidence. The fraction of problems solved by at least one sample grows roughly log-linearly with the number of samples. It took DeepSeek-Coder-V2 on SWE-bench Lite from **15.9% with one sample to 56% with 250** ([Large Language Monkeys](https://arxiv.org/abs/2407.21787)). Among agent runs, picking the one that overthought less improved performance by almost 30% while cutting compute by 43% ([Cuadron et al.](https://arxiv.org/abs/2502.08235)).

On the 4090, run two to four full trajectories in parallel and keep those that pass the code checks: no overlaps, inside free time, no duplicates, and zero remaining goals. Return the passing one with the fewest thinking tokens. If runs were independent, a 0.83 pass rate per run would become 0.97 at two tries and 0.995 at three. Real gains will be smaller, because a scenario the model consistently misreads fails every try. On a batched server, latency is roughly that of the slowest try. On the Mac, at 100–900 seconds per answer, running tries one after another rules this out. The check can only catch what code can see, so best-of-n depends on step 1's goal status.

Swapping models does not beat these fixes. In Qwen's own numbers, the Instruct-2507 sibling trails badly on agent tasks (**TAU2-Airline 24.0 vs 58.0**), and the original Qwen3-8B scores below 4B-Thinking-2507 on BFCL-v3 (68.1 vs 71.2). Qwen3-30B-A3B-Thinking-2507 leads by only +1.2 on BFCL-v3 and +5.3 on TAU2-Retail, and at 30.5B total parameters it needs heavy quantization to fit on a 24 GB card ([Qwen3-4B-Thinking-2507](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507); [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); [Qwen3-30B-A3B-Thinking-2507](https://huggingface.co/Qwen/Qwen3-30B-A3B-Thinking-2507); [Qwen3 report](https://arxiv.org/html/2505.09388)).

Keep Qwen's recommended sampling (temperature 0.6, top_p 0.95, top_k 20, min_p 0). Raise `presence_penalty` toward 1 only if loops persist after the guardrails, since higher values can cause language mixing ([model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)). One worked week-plan example in the prompt is cheap to test, but expect little. SWE-agent's demonstration was worth only 1.7 points ([SWE-agent](https://arxiv.org/html/2405.15793)).

## Self-sampled data and closed-loop RL suit an already-distilled 4B

Four training methods are on the table. **Off-policy distillation** is supervised fine-tuning (SFT) on a stronger model's trajectories, so the student learns to copy what the teacher does in situations the teacher reaches. **Self rejection-sampling fine-tuning (RFT)** samples the student's own attempts, keeps the ones that pass the code checks and fine-tunes on those; the project's collector already does this. In **on-policy distillation**, the student generates and a teacher grades every token through its log-probabilities (its per-token probability scores). **RL with verifiable rewards (RLVR)**, of which GRPO is the common variant, samples a group of attempts per task, scores them with code checks and pushes the model toward the above-average ones.

The deciding fact is how the student was made. Qwen3's small models, the 4B included, were built by "strong-to-weak distillation" from Qwen3-32B or 235B: off-policy first, then on-policy. On Qwen3-8B, the on-policy phase beat RL (**AIME'24 74.4 vs 67.6**) using **1,800 instead of 17,920 GPU-hours** ([Qwen3 report](https://arxiv.org/html/2505.09388)). The model already carries a Qwen teacher's thinking style. Another round of imitation would push an already-distilled model toward a second teacher.

For students near this size, imitating strong reasoners has documented downsides. Training Qwen2.5 students on long rather than short chains of thought changed math scores by **−3.1 points at 3B** and +1.7 at 7B. This "learnability gap" closed when short traces were mixed in at about 1:4 (+5.6 at 3B) ([Li et al.](https://arxiv.org/html/2502.12143v3)). Off-policy students only see situations the teacher reaches, so their own early mistakes compound, and they "can learn to imitate the teacher's style and confidence but not necessarily its factual accuracy" ([Thinking Machines](https://thinkingmachines.ai/blog/on-policy-distillation/)).

Tool calling shows the same pattern. In ToolRL, SFT on 400 reasoning traces distilled from DeepSeek-R1, followed by GRPO, did worse than GRPO alone on every model tested. Qwen2.5-7B scored **39.25 vs 58.38** on BFCL v3: the SFT-first models reached higher training reward but generalized worse ([ToolRL](https://arxiv.org/html/2504.13958)). Tool-N1 likewise found that R1-trace SFT produced "imitative reasoning that limits generalization" ([Tool-N1](https://arxiv.org/html/2505.00024v2)).

The positive counterexample is instructive. APIGen-MT trained its xLAM-2 models only on multi-turn trajectories that passed an execution check. They reached **38.2 (3B) and 46.7 (8B) on tau-bench**, against 24.7 for Qwen2.5-32B-Instruct ([APIGen-MT](https://arxiv.org/html/2504.03601)). What made it work was checking the trajectories, not the teacher's brand. Most clean head-to-head comparisons are on math, and the multi-turn agent evidence is a handful of 2025–2026 papers, so treat the transfer to Steady as likely, not proven.

### Step 2: self-RFT, already built, needs a wider task mix

Self-RFT is the cheapest option that stays on the model's own distribution, and it is already built. Rejection samples lifted LLaMA-7B on GSM8K from **35.9% to 49.3%**. The gains were bigger for weaker models and when more distinct reasoning paths were kept ([Yuan et al.](https://arxiv.org/abs/2308.01825)). Self-training on a model's own shortest correct answers cut output by **about 30%** with accuracy unchanged, across five model families ([Munkhbat et al.](https://arxiv.org/abs/2502.20122)). That is the "think less" half of the goal.

The limits are just as clear. RFT learns nothing from tasks the model never solves. Training only on successes narrows the model's range and can lower pass@k, the chance that at least one of k tries succeeds ([Zhu et al.](https://arxiv.org/abs/2506.01347)). Even SFT on a model's own samples degrades instruction-following at practical learning rates ([Thinking Machines](https://thinkingmachines.ai/blog/on-policy-distillation/)).

In concrete terms, collect through the fixed harness and raise tries from 4 to 8 for multi_goal and weekly_goal tasks, so the hard tasks get some passes. Keep the shortest pass plus one structurally different pass (a different tool order or slot choice), which needs a small collector change, and aim for 300–500 tasks. The existing LoRA settings stay as they are: rank 16, alpha 32, learning rate 1e-4, 2 epochs, loss on the model's own turns. Train one version with and one without the reminder-cut examples (`--skip-reminded`), compare them paired, and stop after one or two rounds.

The current session collects 100–150 tasks at four tries in its 60-minute window, for about $2 in total on a 4090 ([training notes](../ai/notes/training.md)). Extrapolating from that, a 300–500-task run with eight tries on hard types should take three to five GPU-hours, about $2–5.

### Step 3: a short GRPO run that closes the tool loop

GRPO targets the failures RFT cannot reach: loops, missed goals, and proposing only after a reminder. It can do that because it also learns from failed attempts, but only if rollouts run the real multi-turn loop. A NeurIPS 2026 workshop study found that seven single-turn RLVR objectives did nothing for a 2B agent. Multi-turn GRPO that actually executed the tool loop raised task completion from **4.3% to 58.7%**, with **48 of the 52 points gained by step 25**. The same study found that two infrastructure bugs each moved scores by 10–14 points ([When the Loop Closes](https://neurips.cc/virtual/2026/171163)).

For strong 4B models, the gains are small and fragile. MT-GRPO lifted Qwen3.5-4B on tau-bench airline only from **63.8 to 66.7**, and naive per-turn rewards made results up to 14 points worse ([MT-GRPO](https://arxiv.org/abs/2604.02869)). Plain GRPO **dropped Qwen3-4B-2507 on BFCL multi-turn from 48.00 to 41.62**, while its outputs collapsed to about 125 tokens ([ResT](https://arxiv.org/html/2509.21826)).

Two findings shape the reward. Tool-N1's simple binary reward (pass only with well-formed thinking and a well-formed tool call) beat its partial-credit variants, and dropping the format requirement cost about 3 points ([Tool-N1](https://arxiv.org/html/2505.00024v2)). Standard GRPO's averaging also inflates the length of wrong answers, and the Dr. GRPO variant removes that bias ([Dr. GRPO](https://arxiv.org/abs/2503.20783)). LoRA is not a handicap for RL. It matches full fine-tuning for this kind of RL even at rank 1, with a best learning rate about 10× the full-fine-tuning rate, applied to all layers including the MLP layers ([LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)).

Build the GRPO loop around the existing code rather than inside a framework's own loop, so rollouts run exactly the production agent: 8 rounds, the salvage fix, the same prompts. The workshop paper's 10–14-point infrastructure bugs are the reason. In that loop, vLLM serves the base model with `--enable-lora --max-lora-rank 64` and `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1` and hot-reloads each new adapter ([TRL distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)). The agent loop runs eight rollouts per task and records vLLM's token IDs and log-probabilities for every turn. The existing `train_lora.py` masking and chunked loss then compute a group-normalized policy-gradient loss on the model's own tokens. Never re-render the text through the chat template: it auto-inserts `<think>` and strips earlier thinking ([model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)), so a re-rendered conversation won't match what the model actually sampled.

If writing that loss proves slow, there are two alternatives. TRL's `GRPOTrainer` with `environment_factory` maps the four tools onto an environment class with `reset()` and `get_reward()` ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). OpenPipe's ART packages the same LoRA hot-reload pattern ([ART](https://github.com/OpenPipe/ART)).

Rent a 48 GB L40S rather than a 4090, at about the same hourly price. By my arithmetic from the model's 36 layers and 8 KV heads, one 16k-token trajectory holds about 2.3 GB of KV cache (the server's per-token memory of the conversation so far). A 24 GB card can therefore keep only four to six trajectories in flight, and TRL's colocated mode also holds two copies of the weights ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)).

| Setting | Starting value | Basis |
|---|---|---|
| Loss | Dr. GRPO-style constant normalization (or TRL `loss_type="dapo"`), no KL term (`beta=0`) | Removes length bias; LoRA itself limits drift ([TRL](https://huggingface.co/docs/trl/main/en/grpo_trainer); [Dr. GRPO](https://arxiv.org/abs/2503.20783)) |
| Clipping | `epsilon=0.2`, `epsilon_high=0.28` | TRL default plus DAPO's clip-higher ([TRL](https://huggingface.co/docs/trl/main/en/grpo_trainer)) |
| Group | 8 rollouts per task (4 if memory-bound), 2–4 tasks per step | Groups with mixed results carry the signal |
| Rollouts | Temperature 1.0; thinking capped at 4–8k per round; 8 rounds; nudge off | Variety within groups; controls cost; teaches proposing without a prompt. Evaluate at 0.6 |
| Reward | 1 if every code check passes, else 0. 0 for unclosed thinking or malformed calls. Truncated rollouts masked out | Binary reward beat partial credit; per-turn shaping cost up to 14 points ([Tool-N1](https://arxiv.org/html/2505.00024v2); [MT-GRPO](https://arxiv.org/abs/2604.02869)) |
| Anti-gaming checks | Fail on extra events (precision, not just coverage), on proposing before reading the schedule, and on proposing for fixed events | Stops "propose everything" reward hacking |
| LoRA | Rank 16–32, alpha 32, all linear layers; constant learning rate 1e-5 (sweep 5e-6 to 2e-5); gradient clip 1.0 | The 10× rule for LoRA ([LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)) |
| Tasks | Only tasks with 1–3 passes out of 4 in the RFT collection | Groups that all pass or all fail give zero signal |
| Stopping | Held-out eval every 10–25 steps; keep the best checkpoint; stop by step 100 | Gains saturated by step 25 in the 2B study |

My rough estimate is 3.5–7 minutes per step for 32 trajectories, which puts 100 steps at **6–12 hours, about $5–12 on an L40S**. A 30-step smoke test costs about $0.50–1. Unsloth advises waiting "at least 300 steps for reward to increase" ([Unsloth RL guide](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide)). A model that already passes most tasks should show signal sooner, but nobody has measured that for this setup, so the smoke test should confirm the reward moves before you pay for the long run. Keep the RFT adapter as the fallback.

### On-policy distillation is a repair tool here, not a main step

On-policy distillation is the strongest method in the math literature, but it fits poorly here for now. It needs a teacher that is better on this task and that shares the student's tokenizer. TRL's docs say "Every teacher must share the student's tokenizer"; otherwise training silently targets the wrong tokens ([TRL distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)). TRL's trainer also needs the teacher, the student's vLLM server and the trainer on separate GPUs.

The obvious same-family teacher, Qwen3-30B-A3B-Thinking-2507, roughly ties the 4B on BFCL-v3 (72.4 vs 71.2) and TAU2-Airline (58.0 vs 58.0), so it may have little to pass on ([30B card](https://huggingface.co/Qwen/Qwen3-30B-A3B-Thinking-2507)). On reasoning that uses tools, naive on-policy distillation suffers from erroneous tool calls that cascade ([SOD](https://arxiv.org/html/2605.07725v1)). A thinking teacher also pulls the student toward its own, probably longer, thinking, which is the opposite of "think less".

Its best cheap use is repair. If a LoRA damages general behavior, on-policy distillation from the original model can undo it. After code SFT, it restored Qwen3-4B's IFEval score from **79.5 to 82.8** without losing the coding gain ([HF on-policy distillation](https://huggingfaceh4-on-policy-distillation.hf.space/)). In that case the teacher is just the base 4B, which fits on the same pod. Thinking Machines' hosted Tinker service does not list Qwen3-4B-Thinking-2507, so any adapter it trains would be for a different model ([Tinker pricing](https://thinkingmachines.ai/tinker/pricing/)).

## Gemini fails on terms, reasoning traces, and value

### The terms forbid it without Google's permission

The Gemini API terms in effect since March 23, 2026 state: "**You may not use the Services to develop models that compete with the Services.**" There is no research, non-commercial or educational exception. Paying for the API changes how Google uses your data, not this restriction ([Gemini API terms](https://aistudio.google.com/docs/terms)). Vertex AI's terms are stricter. They bar using output to "substitute, replace, or circumvent the use of a Google Model, directly or indirectly" or to "create or improve models similar to a Google Model" ([Google Cloud service terms](https://cloud.google.com/terms/service-terms)). A planner trained on Gemini output, so that the app never has to call Gemini, is close to that wording.

In February 2026, Google's threat-intelligence group wrote that "**distillation from Google's Gemini models without permission is a violation of our Terms of Service**". It named "researchers seeking to clone proprietary logic" among the extraction attempts it blocks, and described defenses that "can degrade student model performance" ([GTIG](https://cloud.google.com/blog/topics/threat-intelligence/distillation-experimentation-integration-ai-adversarial-use)).

The opposing case deserves a hearing. A 4B planner inside one club app is not offered as a competing API, and a few hundred trajectories is tiny next to the 100,000-prompt campaigns Google described. But Google decides what "compete" means. The realistic penalty, suspension of the club's account on suspicion alone, would land on the students. The same terms also require API users to be 18 or older ([Gemini API terms](https://aistudio.google.com/docs/terms)). The conservative reading, and this report's, is that the plan needs Google's written permission. This is not legal advice.

### Gemini doesn't return the reasoning a thinking student needs

Even with permission, the data would be thin. Since around May 2025, the API returns optional thought summaries rather than raw reasoning: "By default, only the final output is returned". You are still billed for all of the hidden thinking ([Gemini thinking docs](https://aistudio.google.com/docs/thinking); [Google AI forum](https://discuss.ai.google.dev/t/massive-regression-detailed-gemini-thinking-process-vanished-from-ai-studio/83916)). Multi-turn function calling on Gemini 3 also requires you to pass back encrypted "thought signatures", and the API returns HTTP 400 errors when they are missing. Injecting synthetic conversation history requires a bypass value that Google calls a last resort that hurts performance ([Vertex thought signatures](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thought-signatures?hl=de)).

For a thinking-only student whose template always opens `<think>`, that leaves three poor choices. **Empty thinking** teaches the model to skip reasoning. **Headline-style summaries** describe reasoning instead of doing it. **Having the 4B regenerate its own thinking** toward Gemini's chosen action, STaR-style rationalization ([STaR](https://arxiv.org/abs/2203.14465)), reduces Gemini to an answer key. Gemini also cannot return log-probabilities over Qwen's vocabulary, which rules out on-policy distillation. The one precedent points the same way: s1.1 beat s1 by replacing its Gemini reasoning traces with DeepSeek-R1 traces on the same questions ([s1](https://github.com/simplescaling/s1)).

### Cheaper open-weight teachers beat it

Gemini is not even the strongest teacher the club can afford. On BFCL V4 multi-turn, Gemini-3-Pro-Preview scores **63.12%** with native function calling, while the open-weight GLM-4.6 scores 68.00% and the small xLAM-2-8b scores 70.00%. Gemini 2.5 Flash scores 36.25%, and Flash-Lite scores **13.50%**, below Qwen3-4B-Instruct-2507's 22.12% ([BFCL leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html)). The cheap Gemini tiers are weaker than the student's own model family. The strong tier costs far more than the club's budget.

The cost figures rest on each research note's own token assumptions: about 30k input and 8k output tokens per Gemini trajectory, and about 25k and 5k per open-weight trajectory. They are not measurements. Price trackers also disagree, so run about 20 pilot trajectories and read the real token usage before spending.

**Verdict: don't do it.** It is the worst-ranked option on terms, on data quality and on value for money. The one gap a frontier teacher could genuinely fill is tasks the 4B never solves even after the harness fixes and RFT. Qwen3-235B-A22B-Thinking-2507 fills that gap legally, in the student's exact format, with full thinking. It scores **TAU2-Telecom 45.6 vs the 4B's 27.2**, at about $0.23 input and $2.30 output per million tokens on OpenRouter ([235B card](https://huggingface.co/Qwen/Qwen3-235B-A22B-Thinking-2507); [OpenRouter](https://openrouter.ai/compare/qwen/qwen3-235b-a22b-thinking-2507)).

If you use it, use it only on tasks the 4B fails eight of eight times after steps 1–2. Filter its trajectories with the same code checks, keep the shortest pass, and mix about one teacher trace for every four of the student's own, the ratio that worked in Mix Distillation ([Li et al.](https://arxiv.org/html/2502.12143v3)). Confirm that the API provider returns reasoning alongside tool calls, and read that provider's own terms, since hosted APIs can add terms beyond the model license. DeepSeek-R1-0528's model card explicitly permits distillation, but its BFCL multi-turn score is 37.0 and its format differs from the student's ([DeepSeek-R1-0528](https://huggingface.co/deepseek-ai/DeepSeek-R1-0528)).

If the club still wants Gemini, the only defensible version is this: written permission from Google, the paid tier (the free tier lets human reviewers read prompts), synthetic calendars only, and Gemini used as an answer key while the 4B regenerates its own thinking. At that point Gemini offers nothing the Qwen teacher doesn't.

## Twelve trials can only detect a 40-point jump

### Why the current suite can't settle anything

Today's suite cannot tell variants apart. A Wilson interval is a confidence range built for small samples, where the usual "±2 standard errors" is too narrow ([Bowyer et al.](https://arxiv.org/html/2503.01747v3)). The 95% Wilson interval around **10/12 runs from 55% to 95%**, and around 9/12 from 47% to 91%. A Fisher exact test of 9/12 against a perfect 12/12 gives **p = 0.22**. The paired McNemar test, which counts scenarios fixed versus broken, needs at least six fixes and zero breaks to reach p < 0.05. Any change smaller than about 40 points is invisible.

The 12 trials are also really six clusters of correlated runs, so the effective sample is smaller still ([Miller](https://arxiv.org/html/2411.00640v1)). The literature predicts single-digit gains for a strong 4B, and multi-turn tool scores shift with seed, system prompt and template construction ([ICML 2026 tool-calling study](https://arxiv.org/abs/2606.00135)).

### What the held-out set should contain

Build 60–100 held-out scenarios spread across categories: week plans with matching events already on the calendar, multi-goal requests, moves, fixed events that must not move, due-tonight requests, no-feasible-slot cases where the right answer is a partial plan or a decline, and ambiguous requests. Generate them from templates, calendar archetypes and phrasings that don't overlap with the training generator; different seeds alone are not enough. Add requests that club members write in their own words. Anthropic relies on held-out test sets for exactly this reason ([Anthropic, writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)).

Include negative cases where the correct behavior is to propose fewer items or none, because "one-sided evals create one-sided optimization". Give each scenario a reference solution that proves it can be solved ([Anthropic, agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Grade outcomes, not paths, in the tau-bench style: compare the final pending proposals against an explicit goal spec listing required items, forbidden overlaps, events that must not move, and an acceptable range for the number of proposals ([tau-bench](https://arxiv.org/html/2406.12045)). Freeze the set, record its hash in every eval log, and never feed its failures into training.

### How to run and compare variants

Run each variant three times per scenario, from a clean calendar, on the same scenarios as the baseline. Use the production sampling settings: lowering the temperature to cut variance measures a different system ([Miller](https://arxiv.org/html/2411.00640v1)). For each variant, report pass^1 with a Wilson or Beta(1+S, 1+N−S) interval, and **pass^3**, the chance that all three runs pass. A planner students rely on has to be consistent, and a 75% per-run pass rate gives a pass^3 of only **42%** ([Anthropic, agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Add pass rates per category, the paired difference from the baseline (McNemar or a paired Bayesian model), and cost: median and 90th-percentile thinking tokens, seconds, rounds, nudge rate, and how often the unclosed-thinking salvage fires.

At 300 trials and 80% accuracy, the interval narrows to about **±4.5 points**. A paired design can detect a change that fixes 12% and breaks 2% of items with about 108 scenario-trials. Spend any extra budget on more scenarios, not on more than three or four repeats. Use one decision rule throughout: adopt a change only when fixed scenarios outnumber broken ones at p < 0.05 (or the probability of improvement is above 0.95) and no regression gate fails.

### Regression checks after any fine-tune

After any LoRA, also run the original six scenarios as a regression gate that should sit at 100%, plus 100–200 BFCL v3 items (including the multi-turn and irrelevance categories), about 100 IFEval prompts, and about 20 off-topic chats checked by hand for format, language mixing and refusals. The IFEval check matters: SFT of Qwen3-4B on code data cost it nearly 4 IFEval points ([HF on-policy distillation](https://huggingfaceh4-on-policy-distillation.hf.space/)). Read the transcripts of every failure; that is how the project's four known failure types were found. Finally, make the RL rollout loop, the collector and the eval harness one shared code path. A mismatch in the loop or template alone can move multi-turn scores more than any method in this report ([When the Loop Closes](https://neurips.cc/virtual/2026/171163)).

## Conclusion

The question was framed as which teacher to learn from, but the evidence shifts it to what the 4B is actually missing. It already scores close to its larger siblings on agent benchmarks and was itself distilled from them, so any teacher has little left to add. What it lacks is composite requests in its training data and reliable bookkeeping inside the loop. Both are cheaper to supply in code than in weights. The order of the steps matters more than any single method. Harness fixes create the partial successes RFT can keep and the mixed groups GRPO needs. RFT's shorter thinking cuts the cost of every GRPO rollout. GRPO then works on whatever failures neither of them reached.

That also makes the Gemini idea unnecessary, not just risky. The frontier-quality signal it promised is available from Qwen's own larger models: legally, in the right format, with full reasoning, and for less money. The project's largest gains will probably come from code the model never has to learn. The real unknown is how big each gain will be. Every expected effect here is an estimate drawn mostly from math benchmarks and frontier-model studies, which is why the held-out eval comes first.

# RL / On-Policy Distillation Tooling and Compute for a 4B Thinking Tool-Calling Agent (Qwen3-4B-Thinking-2507, $10–30 budget)

Research date: 2026-11-05. Versions seen in docs: TRL v1.17.1 docs (transformers v5.22.1 links), TRL `main` GRPO docs, verl docs last updated 2026-05-09, Tinker pricing dated 2026-10-19. Project context checked locally: `ai/pyproject.toml` pins `transformers>=5.18.0`; `ai/deploy/runpod_train.sh` pins `peft==0.21.2` and installs vLLM in its own venv; `ai/notes/training.md` describes the current rank-16/alpha-32 LoRA SFT on the model's own turns and serving the adapter via vLLM `--enable-lora`.

## Q1. Which frameworks support multi-turn / agentic RL (and on-policy distillation) in 2026, and how does each plug in a custom Python tool environment?

### Takeaway
For one GPU and a custom Python calendar environment, the realistic options are (a) TRL `GRPOTrainer` with `environment_factory` (native multi-turn tool loop, Qwen3-aware template patching, vLLM colocate or server), optionally with Unsloth's memory patches, (b) a custom "ART-style" loop (your own agent loop + vLLM LoRA hot-reload + a GRPO loss), or ART itself, which packages that pattern. verl, SkyRL, rLLM and Agent Lightning all work, but they are built around Ray and multiple GPUs, which is too much for this budget. Tinker is a hosted API whose price list has no Qwen3-4B-Thinking-2507 (only Qwen3-8B and Qwen3.5-4B), so any adapter it trains would be for a different base model.

### Cited Findings
**Hugging Face TRL (GRPOTrainer, docs `main` / v1.x)**
- `GRPOTrainer` takes `tools=[...]`: plain Python functions (sync or async) with type hints and Google-style docstrings. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `environment_factory` is a callable, or a `dict[str, Callable]` for multiple environments, that builds one stateful environment instance per rollout. Its public methods become tools. Reserved methods are `reset(**kwargs)` (required; it returns None or a string that becomes the prompt) and `get_reward()` (optional; it returns a float once per finished rollout). It requires `transformers>=5.2.0`. If `train_dataset` is omitted, `max_steps` must be set. With a dict, a dataset column `environment` picks the environment per row. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `max_tool_calling_iterations` caps the number of tool turns (default None, no limit). Generation stops when a turn contains no tool calls. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `rollout_func` is experimental ("may change or be removed at any time"). It must return `prompt_ids`, `completion_ids` and `logprobs`, plus optionally `logprob_token_ids`. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- Per TRL's docs (as summarized in search results), `max_completion_length` limits the total tokens across the whole multi-turn conversation, tool results included. — [TRL OpenEnv docs v1.6.0](https://huggingface.co/docs/trl/v1.6.0/openenv)
- A PyTorch Conference EU 2026 talk describes the same contract: one environment instance per generation, the reward stored on the instance and read back by `reward_func(environments, **kwargs)`, and a loop that runs until there are no tool calls or `max_tool_calling_iterations` is reached. — [PyTorch Conf EU 2026 slides](https://hosted-files.sched.co/pytorchconferenceeu2026/c3/From%20Responses%20To%20Trajectories_%20Multi-Turn%20and%20Multi-Environment%20Reinforcement%20Learning.pdf)
- Version caveat: a 2026 arXiv paper reports that TRL 0.22.2 made a single generation call per rollout with no native tool loop, so its authors wrote their own driver. The native loop is a TRL 1.x feature. — [arXiv 2607.11954](https://arxiv.org/pdf/2607.11954)
- TRL lists Qwen3 and Qwen3.5/3.6 as tested models. With tools enabled, it substitutes a patched "prefix-preserving" training template for known families such as Qwen3 and DeepSeek-V3. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- On-policy distillation in TRL: `DistillationTrainer`, `ServerDistillationTrainer` and `experimental.async_distillation.AsyncDistillationTrainer` (v1.17.1). The async trainer has a background rollout worker for student generation and teacher scoring, takes the teacher only as a vLLM server URL, supports a `peft_config` (LoRA), and accepts a custom `rollout_worker` (`RolloutWorkerProtocol`). — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)

**OpenPipe ART (Agent Reinforcement Trainer)**
- ART is an open-source GRPO harness for multi-step agents (Apache-2.0). Your own code runs the agent workflow and stores each system/user/assistant message in a Trajectory. When a rollout finishes, your code assigns the reward. Trajectories are grouped and sent to the server, and inference pauses while training runs. — [OpenPipe/ART](https://github.com/OpenPipe/ART)
- Each training step saves a new LoRA to a local directory and loads it into vLLM. The next step starts from the latest LoRA (an empty LoRA on the first iteration). — [OpenPipe/ART](https://github.com/OpenPipe/ART)
- ART credits Unsloth, vLLM, TRL and torchtune. It says it supports "most vLLM / HF-transformers compatible causal LMs, or those supported by Unsloth" (Gemma 3 is noted as unsupported). Current README examples are serverless (W&B) Qwen 3.x notebooks, and older local notebooks use Qwen 2.5 3B/7B/14B. The README gives no GPU, time or cost figures, and the GitHub Releases section is empty. — [OpenPipe/ART](https://github.com/OpenPipe/ART)
- RULER provides "automatic reward generation" (an LLM judge). The project does not need it because its reward is verifiable. — [OpenPipe/ART](https://github.com/OpenPipe/ART)
- Secondhand claim: a 14B model trained with ART on one GPU for under $80 beat OpenAI's best model on an agentic task. This comes from a third-party summary of OpenPipe's own benchmark, so it is vendor-sourced. — [Daily Dose of DS](https://blog.dailydoseofds.com/p/art-train-agents-that-can-learn-from)

**verl (and verl-based: verl-agent, rLLM, Agent Lightning)**
- verl multi-turn: custom tools subclass `verl.tools.base_tool.BaseTool` (with `create`/`execute`) and are configured in YAML via `actor_rollout_ref.rollout.tool_kwargs.tools_config_file`. Stateless tools can instead use `@function_tool` with `agent.default_agent_loop: tool_agent`. `ToolAgentLoop` handles tool turns, and custom loops go in `agent.agent_loop_config_path`. The doc example uses the SGLang engine. — [verl multi-turn docs](https://verl.readthedocs.io/en/latest/sglang_multiturn/multiturn.html)
- verl builds multi-turn tokens with delta-based tokenization: only new assistant tokens get `loss_mask=1`, so tool and user tokens are excluded. A tokenization sanity check runs with modes `strict` (default), `ignore_strippable` and `disable`. — [verl multi-turn docs](https://verl.readthedocs.io/en/latest/sglang_multiturn/multiturn.html)
- verl-agent (built on verl) supports Qwen3 and LoRA and "now supports training 7B models using 2 H100 GPUs". — [verl-agent](https://github.com/langfengQ/verl-agent)
- rLLM uses verl as its backend (per the SkyRL-Agent paper's comparison table). — [SkyRL-Agent paper](https://arxiv.org/html/2511.16108v1)
- Agent Lightning (Microsoft) is middleware between RL algorithms and existing agents ("without code rewrites"). Its GPU needs depend on the training backend it connects to. — [Microsoft Research](https://www.microsoft.com/en-us/research/?p=1158079)
- verl also ships on-policy distillation (OPD) docs: teacher scoring of the prompt+response prefix with a raised max-logprobs cap, and an async OPD variant. — [verl OPD docs](https://verl.readthedocs.io/en/latest/_sources/algo/opd.md.txt); [verl async OPD](https://verl.readthedocs.io/en/latest/_sources/advance/async-on-policy-distill.md.txt)

### Inferences
- Best fit for this project: TRL `environment_factory` maps almost directly onto the existing Python tools (`get_schedule`, `find_free_slots`, `propose_new_event`, `propose_move_event`). Wrap the fake calendar in a class whose public methods are the tools, have `reset(**task)` build the week and question, and have `get_reward()` run the existing success checks. The open question is whether Unsloth's TRL patching works with TRL 1.x `environment_factory` (see Gaps).
- The lowest-dependency path is a custom ART-style loop. The repo already has the agent loop, vLLM serving with LoRA (`--enable-lora`) and a PyTorch LoRA script. Adding GRPO means: (1) capture token IDs and sampled logprobs from vLLM for every assistant turn, (2) group rollouts per task (G=4–8) and compute group-normalized advantages, (3) apply a token-level clipped policy-gradient loss masked to assistant tokens, (4) save the adapter and hot-reload it in vLLM. This gives the most control over Qwen3 template handling (Q5), but you have to write and debug the GRPO loss yourself.
- verl, SkyRL, rLLM, OpenRLHF and Agent Lightning are overkill for one GPU and $10–30. They assume Ray and multi-GPU, and their documented minimums are 2xH100 for 7B (verl-agent) and 4 GPUs (SkyRL quickstart).
- Tinker removes the GPU work, but it cannot train Qwen3-4B-Thinking-2507. You would train Qwen3-8B (32K context) or Qwen3.5-4B, then serve that base plus adapter in vLLM. That changes the deployed model.

### Gaps
- Not verified: whether Unsloth's `PatchFastRL`/GRPO integration supports TRL 1.x `environment_factory` or `tools` (no Unsloth doc mentions multi-turn tool RL), and whether Unsloth's `fast_inference` (vLLM) path covers the Qwen3-4B-Thinking-2507 checkpoint specifically (it has a "Qwen3 (4B)" notebook, model variant unconfirmed).
- OpenRLHF was not researched (no time). Its multi-turn and agent support is unknown here.
- ART's LocalBackend GPU requirements, current version, and handling of Qwen3 thinking tokens across turns are not documented in the README.
- Whether Tinker lets you download trained LoRA weights for use in your own vLLM was not verified in this research.
- Exact `rollout_func` signature and semantics in the installed TRL version: experimental and under-documented.

## Q2. What GPU, how many steps, how long per step, and how many dollars for LoRA GRPO on a 4B model with G=4–8 and 8–16k-token trajectories?

### Takeaway
A single 24 GB 4090 is probably enough with Unsloth-style weight sharing and chunked logits, but only with small groups, micro-batch 1, and few concurrent rollouts. Plain TRL colocate, which keeps two weight copies plus unchunked logits, is unlikely to fit 16k trajectories on 24 GB. A 48 GB L40S costs about the same per hour on RunPod and is the better choice. A rough estimate (my arithmetic, not a measured benchmark) is 3–8 minutes per step for 32 trajectories of ~8k tokens on a 4090/L40S class GPU, so 100 steps cost about $5–12 and 300 steps about $15–35. Unsloth says to expect at least 300 steps before reward rises on hard tasks. A task where the base model already passes most checks (11/12 in Stage 3) should show signal sooner, but sparse wins are needed for any learning at all.

### Cited Findings
**Model facts**
- Qwen3-4B-Thinking-2507: 36 layers, GQA with 32 query heads and 8 KV heads, 4.0B params (3.6B non-embedding), native context 262,144. — [Qwen3-4B-Thinking-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)

**Unsloth memory claims (vendor, not independently reproduced)**

Recommended `gpu_memory_utilization` is 0.90–0.95; 1.0 fails. — [Unsloth Memory-Efficient RL](https://unsloth.ai/docs/new/memory-efficient-rl)

Without Standby it OOMs at util 0.9/0.8 even at batch 1, and at util 0.7 it fits at about 15.1 GiB. The T4 runs used `num_generations=2`, grad-accum 2, and took 28–29 steps in about 40 min. — [Unsloth Memory-Efficient RL](https://unsloth.ai/docs/new/memory-efficient-rl)

Qwen3-32B LoRA on an H100 80GB reaches 6,144 context (x2 generations). Techniques are flattened sequence chunking of logits (`unsloth_logit_chunk_multiplier`, default `max(4, context_length // 4096)`), hidden-state batch chunking (`unsloth_grpo_mini_batch`) and offloading log-softmax activations. ### Inferences
Assumptions are marked. They come from standard Qwen3 config values and GPU specs not re-verified in this research, so treat every number below as an estimate to check with a short benchmark run.
- **KV cache per token**, assuming head_dim=128: 2 x 36 layers x 8 KV heads x 128 x 2 bytes ≈ 144 KiB/token. A 16k-token trajectory therefore holds about 2.3 GB of KV, so a 24 GB card with about 8 GB of BF16 weights can keep only about 4–6 such trajectories in flight. A 48 GB card can keep about 15–20, which shortens the generation phase roughly in proportion. This is consistent with Unsloth's T4 figure of about 32K KV tokens in about 6 GB beyond the weights.
- **Logits are the hidden OOM**, assuming a vocab of about 152K: unchunked fp32 logits for one 16k-token sequence are about 16k x 152K x 4 B ≈ 9.7 GB. That alone explains why plain HF/TRL OOMs on 24 GB at long context, and why Unsloth's chunking matters.
- **TRL colocate on 24 GB** holds two weight copies (vLLM plus trainer, about 16 GB) before any KV cache or activations. That is unlikely to fit 8–16k trajectories without QLoRA, sleep mode and a low `vllm_gpu_memory_utilization`. TRL server mode needs two GPUs (one for vLLM, one for training), which roughly doubles $/hr.
- **Rough per-step estimate** (G=8, 4 tasks per step = 32 trajectories, about 6k generated plus about 8k total tokens each): generation is about 190k sampled tokens. At an assumed aggregate of 1–2.5k tok/s for a 4B model with LoRA on a 4090/L40S at modest concurrency, that is about 1.5–3 minutes. Training is about 256k tokens x about 6 x 4e9 FLOPs ≈ 6e15 FLOPs (forward plus backward plus checkpoint recompute). At an assumed effective 30–50 TFLOP/s, that is about 2–3.5 minutes. The total is about 3.5–7 minutes per step. Halving the group or task count roughly halves this.
- **Cost estimate:**

| Plan | Steps | Est. wall-clock | 4090 Secure @ $0.89 | 4090 Community @ $0.34 | L40S @ ~$0.86 |
|---|---|---|---|---|---|
| Smoke test (G=4, 2 tasks/step) | 30 | ~0.5–1 h | ~$0.5–1 | ~$0.2–0.4 | ~$0.5–1 |
| Small run (G=8, 4 tasks/step) | 100 | ~6–12 h | ~$5–11 | ~$2–4 | ~$4–9 (likely faster due to more KV room) |
| Unsloth-recommended (G=8, 4 tasks/step) | 300 | ~18–35 h | ~$16–31 | ~$6–12 | ~$13–26 |

- **H100 SXM** (~$2.69–3.99/hr) is probably 3–4x faster per step (assumed), so the total $ comes out similar and wall-clock is much shorter. It is worth it if pod time is supervised by a person.
- **Tinker rough cost** for the same 32x8k step on Qwen3-8B: about 190k sampled ($0.11), about 0.5M prefill from multi-turn re-prefill ($0.10) and about 256k trained ($0.11), so about $0.33/step. That is about $16 for 50 steps and about $33 for 100 steps, at the 32K context cap. The prefill multiplier for multi-turn is an assumption.
- The current base model already passes 11/12 Stage 3 evals, so most groups will have mixed outcomes, which gives GRPO a useful signal. But groups where all 8 rollouts pass or all fail give zero advantage. The train set should therefore favor tasks the model sometimes fails, such as "propose directly without the reminder". This can make fewer than 300 steps useful, but that is unverified.

### Gaps
- No independent measured VRAM or step-time numbers were found for Qwen3-4B multi-turn GRPO at 8–16k tokens on a 4090 or L40S. All Unsloth numbers are vendor benchmarks on short single-turn tasks.
- vLLM throughput for Qwen3-4B on a 4090/L40S with LoRA at a given concurrency was not sourced. The per-step estimate depends on it, so measure it with the existing `collect_traces.py --workers N` runs, which already exercise vLLM on RunPod.
- RunPod prices were taken from aggregator and snapshot quotes, not a live fetch of runpod.io.

## Q3. Recommended hyperparameters for small-model tool-use GRPO with LoRA

### Takeaway
Start from TRL 1.x defaults: `loss_type="dapo"` (token-level normalization), `beta=0.0` (no KL and no reference model), `epsilon=0.2`, `num_iterations=1`, and vLLM importance-sampling correction on. Add `epsilon_high=0.28` (DAPO clip-higher) and `mask_truncated_completions=True`. Use G=8 (G=4 if memory-bound) and LoRA on all linear layers, MLP included. Per "LoRA Without Regret", use a LoRA LR about 10x the full-fine-tune LR and a constant schedule; rank 8–32 is plenty for RL. Shape the reward as a verifiable success score plus small format and partial-credit terms. Set `max_completion_length` to the whole multi-turn budget (about 16k).

### Cited Findings
- TRL `GRPOConfig` defaults (main): `loss_type='dapo'` (token-level normalization 1/Σ|o_i|). `"dr_grpo"` divides by a constant L·G (L = max completion length) to remove length bias. Other options are `"sapo"` (soft gating; `sapo_temperature_pos=1.0`, `sapo_temperature_neg=1.05`), `"cispo"` and `"vespo"`. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `beta` defaults to 0.0 (KL off, no reference model loaded). DeepSeek-R1 used 0.001. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `epsilon=0.2`. `epsilon_high` defaults to None, meaning equal to epsilon, and DAPO recommends 0.28 (ScaleRL recommends 5.0 with `cispo`). `delta` (None) turns on two-sided clipping (INTELLECT-2). — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `num_iterations=1` (μ; with μ=1 the clipped objective reduces to the basic one). `importance_sampling_level="token"` (`"sequence"` gives GSPO). — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `vllm_importance_sampling_correction=True` corrects training/inference mismatch. Mode `'sequence_mask'`, `vllm_importance_sampling_clip_max=3.0`. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- `scale_rewards='group'` by default. `False` disables std scaling (Dr. GRPO, "Understanding R1-Zero-Like Training"), and `"batch"` uses batch-level std (Lite PPO). `mask_truncated_completions` defaults to False. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- Unsloth guidance: `epsilon=0.2`, `epsilon_high=0.28`, `delta=1.5`; loss types `'gspo'`, `'grpo'`, `'dr_grpo'`; `mask_truncated_completions=True`. Its examples use 8 generations and suggest trying 16. It recommends a rubric of several small verifiable rewards rather than one reward, and proximity-based partial credit. — [Unsloth RL guide](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide)
- LoRA for RL (Thinking Machines): LoRA "fully matches" full fine-tuning in policy-gradient RL even at rank 1. The optimal LoRA LR is about 10x the full-FT LR (fitted multiplier about 9.8, and about 15x for short runs under about 100 steps). Apply LoRA to all layers, especially MLP (attention-only underperformed). They used alpha=32 with α/r scaling, which makes the optimal LR roughly rank-independent, and a constant LR with no warmup in RL runs. LoRA may tolerate large batch sizes less well (shown in SL). — [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)
- ToolRL: tool-use GRPO reward decomposed into format adherence plus correctness of tool name, parameter names and parameter values. They report a 17% gain over base and 15% over SFT models. On Qwen2.5-1.5B-Instruct, their reward scored 46.20% versus 40.71% (finer-grained), 37.65% (intermediate) and 36.72% (coarse). — [ToolRL arXiv 2504.13958](https://arxiv.org/html/2504.13958); [ToolRL review](https://liner.com/review/toolrl-reward-is-all-tool-learning-needs)
- Inference sampling recommended for this model: temperature 0.6, top_p 0.95, top_k 20, min_p 0. Presence penalty of 0–2 against repetition. Output length 32,768 for most queries. — [Qwen3-4B-Thinking-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)
- The TRL distillation config defaults to `temperature=1.0` for on-policy sampling and `learning_rate=1e-6` for full models. — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- On-policy distillation reference settings: 4 samples per prompt, 64 prompts per batch, about 150 steps, linear LR schedule (swept, value not given), LoRA rank 32 or 128. — [TM on-policy distillation](https://thinkingmachines.ai/blog/on-policy-distillation/)

### Inferences
- **Proposed starting config** (to verify with a 30-step smoke test): `loss_type="dapo"` or `"dr_grpo"`, `beta=0.0`, `epsilon=0.2`, `epsilon_high=0.28`, `num_iterations=1`, `num_generations=8` (4 if memory-bound), 2–4 tasks per step, `max_completion_length≈16384` (whole conversation), `max_tool_calling_iterations=8` (matching the agent loop's 8 rounds), `mask_truncated_completions=True`, LoRA r=16–32, alpha=32, all linear layers (matches the existing SFT adapter's targets), constant LR about 1e-5 for LoRA (about 10x a typical 1e-6 full-FT RL LR; sweep 5e-6 to 2e-5), and `max_grad_norm` around 1.0.
- **Temperature**: use about 1.0 (or 0.8–1.0) for rollouts to get group diversity. The model card's 0.6 is an inference setting, and evaluation should keep using it.
- **Reward shaping** for Steady: main reward 1.0 if all the task's code checks pass (the same checks as `synth.py`), with small partial credit (such as 0.25 each) for right tool sequence (looked up schedule, searched free slots), valid tool JSON, and correct count of proposals. Add a small negative for malformed `<tool_call>` JSON or for proposing on "move_fixed" tasks. To serve the "think less" goal, add a mild length penalty only on correct rollouts, or use `dr_grpo`, which removes the length bias of per-sequence normalization. Truncated rollouts get reward 0 and are masked.
- **KL**: without a reference model (`beta=0`), the LoRA itself limits drift. Keep evaluating on the held-out evals every 25 steps, and keep the SFT adapter as the fallback.

### Gaps
- No primary source gave an absolute LoRA GRPO LR for Qwen3-4B. The 1e-5 figure is derived from the 10x rule plus TRL's 1e-6 default for full models in the distillation trainer. The GRPOConfig default LR was not verified in this research.
- DAPO's soft overlong punishment and dynamic sampling (filtering all-correct and all-wrong groups) were not checked in the TRL docs. Whether TRL exposes them, and under which names, is unknown here.
- ToolRL's exact learning rate, group size and reward weights were not retrieved (they are in its repo, github.com/qiancheng0/ToolRL).

## Q4. On-policy distillation in practice: requirements, implementations, cost vs RL, and whether a Qwen3-30B-A3B or 235B teacher on vLLM can supply logprobs

### Takeaway
On-policy distillation (OPD) needs only teacher logprobs on the student's own sampled tokens. vLLM supplies these through `prompt_logprobs` with `max_tokens=1`, so a same-tokenizer Qwen3 teacher served by vLLM works. Thinking Machines reports roughly 10x less compute than RL. TRL's async trainer, however, needs teacher, student-vLLM and trainer on separate GPUs, and its docs say nothing about multi-turn tool environments. For this budget, a do-it-yourself, batch-alternating OPD loop, or Tinker's multi-turn tool-use OPD recipe, is more practical. OPD also pulls the student toward the teacher's behavior, including the teacher's long thinking, which works against the project's "think less" goal.

### Cited Findings
- **Mechanism:** the student samples, then the teacher scores each sampled token (`compute_logprobs`, no teacher gradients). Per-token advantage = −(student logprob − teacher logprob), i.e. negative reverse KL, optimized with RL's importance-sampling loss and discount 0. No reward model is needed, partial rollouts work, and reverse KL is described as "unhackable". — [TM on-policy distillation](https://thinkingmachines.ai/blog/on-policy-distillation/)
- **Cost vs RL:** they cite the Qwen3 report: RL took 17,920 GPU-hours versus 1,800 for OPD. On AIME'24, OPD reached 70% with about 8.4e19 teacher plus 8.2e19 student FLOPs, versus SFT-2M (extrapolated, about 70%) at about 3.4e21 plus 1.5e21. They claim about 9x fewer FLOPs than SFT-2M given the data, about 18x in GPU-hours, and about 30x including teacher sampling. In self-distillation, OPD needed about 7–10x fewer gradient steps than RL, which they estimate as 50–100x less compute. — [TM on-policy distillation](https://thinkingmachines.ai/blog/on-policy-distillation/)
- **Settings and results:** Qwen3-8B-Base student, Qwen3-32B teacher (they say Qwen3-8B was used as teacher in practice). 4 samples per prompt, 64 prompts per batch, about 150 steps to reach 70% AIME'24 from a 400K-prompt SFT checkpoint. At rank 32, LoRA trailed full FT by 13% after SFT but only 6% after distillation. — [TM on-policy distillation](https://thinkingmachines.ai/blog/on-policy-distillation/)
- **TRL implementation:** `AsyncDistillationTrainer` minimizes a generalized JSD (`beta=0.0` forward KL by default, `beta=1.0` reverse KL). It is always on-policy, and the teacher is only a vLLM URL. — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **Tokenizer requirement:** "Every teacher must share the student's tokenizer". Completions are sent as raw token IDs, and a teacher with a different vocabulary "trains the student against the wrong tokens, silently". — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **Teacher scoring request:** teacher-forced with `max_tokens=1`, `prompt_logprobs=teacher_top_k`, `temperature=teacher_temperature`. Start the teacher with `vllm serve <teacher> --logprobs-mode processed_logprobs --max-logprobs -1` (the default cap is 20 logprobs). `teacher_top_k` defaults to 8, and 16–64 is suggested for real runs (miles uses 16, EasyOPD 64). A tail bucket covers the remaining mass. At `beta != 0` the support narrows to the teacher's top-1 plus the realized token. — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **GPU layout:** "The teacher server, the student's vLLM server, and the trainer must run on separate GPUs." LoRA (`peft_config`) is supported, and with `--enable-lora` on the student server only the adapter is synced (about 160 MB at r=32) instead of merged weights (about 15 GB for 7B). — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **Install caveat:** vLLM and transformers have conflicting pins. Install vLLM first, then `pip install 'transformers>=5.2.0' --no-deps`. Distributed training supports only FSDP2. — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- Reverse KL is a valid estimate only when the scored tokens were sampled from the student. — [TorchRL DistillationLoss](https://docs.pytorch.org/rl/stable/reference/generated/torchrl.objectives.llm.DistillationLoss.html)
- The same model can give different logprobs for the same sequence in HF Transformers versus vLLM, so the teacher's vLLM logprobs and the student's HF logprobs are not bit-identical. — [DeltaPrompts arXiv 2605.15532](https://arxiv.org/pdf/2605.15532)
- verl OPD has the teacher score the prompt+response prefix (it rewrites `prompt_length := prompt_length + response_length`, `response_length := 1`) with a raised max-logprobs cap. — [verl OPD docs](https://verl.readthedocs.io/en/latest/_sources/algo/opd.md.txt)
- The Tinker cookbook has a multi-turn tool-use OPD recipe (`harbor_multiturn.py`, zero environment reward). — [Tinker cookbook distillation docs](https://tinker-docs.thinkingmachines.ai/cookbook/recipes/distillation/)
- Sending teacher logprobs became a bottleneck in TRL's distillation work, which they addressed by batching and binary-encoding logprobs. — [HF TRL distillation write-up (PDF)](https://huggingfacetb-trl-distillation-trainer.hf.space/distilling-100b-models-40x-faster-with-trl.pdf)

### Inferences
- **Teacher choice:** Qwen3-30B-A3B-Thinking-2507 or Qwen3-235B-A22B-Thinking-2507 should share Qwen3-4B's tokenizer, since they are the same Qwen3 family. Confirm before training by comparing `tokenizer.json` and vocab sizes. If shared, a vLLM server running the teacher can score the student's multi-turn trajectory: send the full token ID sequence (system, user, assistant thinking and tool calls, tool results) as the prompt with `prompt_logprobs=k, max_tokens=1`, then use teacher logprobs only at assistant-token positions (same loss mask as RL).
- **Teacher memory** (assuming about 30.5B params for 30B-A3B): about 61 GB in BF16 needs an 80 GB A100/H100, and FP8 at about 31 GB fits a 48 GB L40S. A 235B teacher is out of budget to self-host, roughly 4–8x80 GB.
- **Budget layout:** TRL's async trainer needs 3 GPUs at once, roughly $3.5–5/hr with an H100 for the teacher. That is feasible for a few hours but eats the budget. A cheaper do-it-yourself option on one 80 GB GPU alternates phases: (1) student vLLM with LoRA samples N trajectories, (2) stop it and start the teacher vLLM to score them, (3) train the LoRA with the per-token reverse-KL advantage in the existing PyTorch script. Loading models into vLLM costs minutes per phase, so use large batches.
- **Fit with goals:** OPD with a thinking teacher pushes the student toward the teacher's thinking, which is likely longer, not shorter. If the main goals are "propose directly" and "think less", RL with a verifiable success reward plus a length penalty on correct answers, or the current SFT-on-shortest-correct-traces, targets them more directly. OPD fits best when the teacher solves tasks the student fails, which is not the case at 11/12 base pass rate. Treat OPD as optional.
- **Tinker OPD** would use Qwen3.5 or Qwen3-8B models, not the deployed Qwen3-4B-Thinking-2507.

### Gaps
- Not verified: whether `AsyncDistillationTrainer` supports multi-turn tool environments. The docs never mention tools; a custom `rollout_worker` is the likely route.
- The tokenizer identity of Qwen3-30B-A3B-Thinking-2507 versus Qwen3-4B-Thinking-2507 was not directly verified.
- No measured cost was found for OPD on agentic multi-turn tasks at 4B scale. The 10x claim comes from math reasoning (vendor blog citing the Qwen3 report).

## Q5. Pitfalls with Qwen3 thinking models in multi-turn RL (templates, masking, vLLM versions, LoRA export)

### Takeaway
The main risks are: (1) retokenization and template drift, because Qwen3's template strips thinking from earlier turns and auto-inserts `<think>`, so re-rendered conversations do not match the sampled tokens; (2) loss masking that must cover only model-generated tokens and exclude tool results; (3) training/inference numeric mismatch between vLLM and the trainer; (4) vLLM/transformers dependency conflicts and server flags. Keep token IDs straight from vLLM, train only on assistant tokens, keep IS correction on, and make sure vLLM's `--max-lora-rank` is at least the adapter rank.

### Cited Findings
- **Auto `<think>`:** for Qwen3-4B-Thinking-2507, the default chat template inserts `<think>`, so the output may contain only `</think>`. — [Qwen3-4B-Thinking-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)
- vLLM's Qwen3 reasoning parser notes that `<think>` is usually in the prompt via the template, so generated text typically has only `</think>`. It also notes template-convention differences across releases, including 2507. — [vLLM qwen3 reasoning parser](https://docs.vllm.ai/en/v0.19.1/api/vllm/reasoning/qwen3_reasoning_parser/)
- **History stripping:** official guidance is to keep only the final answer in history, not the thinking, and the provided Jinja template does this. — [Qwen3-4B-Thinking-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)
- Qwen maintainers say previous-turn thinking should be removed "except for multi-step tool calls", which the official template handles. — [QwenLM/Qwen3 discussion #1398](https://github.com/QwenLM/Qwen3/discussions/1398)
- Newer templates expose a `preserve_thinking` option (mirroring Qwen3.6). — [Luciole-8B template discussion](https://huggingface.co/OpenLLM-France/Luciole-8B-KD-Math-Thinking-1.1/discussions/1)
- verl: Qwen3 and QwQ templates strip reasoning from history, which breaks delta tokenization, so verl falls back to a fixed base conversation. QwQ-32B needs a template revision (`refs/pr/81`). Reasoning is kept in training and rollout by default. `multi_turn.use_inference_chat_template=True` matches production but may mismatch training. Long reasoning can exceed the context window. — [verl multi-turn docs](https://verl.readthedocs.io/en/latest/sglang_multiturn/multiturn.html)
- TRL swaps in a patched prefix-preserving training template for Qwen3 when tools are enabled. Its examples disable thinking with `chat_template_kwargs={"enable_thinking": False}`, which a Thinking-2507 model does not support (it always thinks). — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- **Tool-output masking in TRL:** PR #5390 (`stop_tool_names`) says tool-result tokens appended to `completion_ids` get `tool_mask=0`, keeping them out of the loss. Its merge status was not confirmed. TRL docs say `num_tokens` and completion-length metrics count only non-tool tokens. — [huggingface/trl PR #5390](https://github.com/huggingface/trl/pull/5390); [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- An example of the masking bug class: NeMo RL fixed GRPO loss masks that had unmasked every `role == "assistant"` message. — [NVIDIA-NeMo/RL PR #2176](https://github.com/NVIDIA-NeMo/RL/pull/2176)
- SimpleTIR (multi-turn tool-integrated RL) accumulates loss only over the agent's action tokens and excludes environment feedback. — [SimpleTIR arXiv 2509.02479](https://arxiv.org/pdf/2509.02479)
- **Training/inference mismatch:** TRL enables `vllm_importance_sampling_correction` by default. TRL's async trainers default the student to `dtype="float32"` because the mismatch is precision-sensitive, citing "Defeating the Training-Inference Mismatch via FP16" (arXiv 2510.26788). Fully closing the gap requires serving vLLM in the same dtype. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer); [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **vLLM server mode flags** (TRL): `VLLM_SERVER_DEV_MODE=1 vllm serve <model> --weight-transfer-config '{"backend":"nccl"}' --logprobs-mode processed_logprobs --max-logprobs -1`. Put the server on different GPUs from the trainer to avoid NCCL errors. — [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)
- **LoRA hot-swap in vLLM** (TRL): `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1`, `--enable-lora`, and `--max-lora-rank` from {1, 8, 16, 32, 64, 128, 256, 320, 512}, which sets the maximum rank the server can serve (r=4 works under 8). `--max-loras ≥ max_staleness + 2`. Adapters are loaded from disk, so the path must be visible to the server. `.vllm_lora/` is only a cache, so keep checkpoints on (`save_strategy="no"` loses the trained adapter). — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- **Install conflict:** vLLM and transformers pin conflicting versions. Install vLLM first, then force-install `transformers>=5.2.0 --no-deps`. — [TRL Async Distillation docs](https://huggingface.co/docs/trl/async_distillation_trainer)
- The project's own deploy script notes that a plain `pip install vllm` fails on RunPod's Ubuntu 24.04 PyTorch image, so vLLM lives in its own uv venv. — local file `/Users/diggy/Documents/MSU/AI_club/steady/steady/ai/deploy/runpod_train.sh`
- **Tool-call parsing:** Qwen recommends Qwen-Agent for tool calling, and says to disable the serving framework's reasoning and tool-call parsing when using it. — [Qwen3-4B-Thinking-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)
- In a multi-turn SFT discussion, the loss is computed only on assistant replies while several think blocks are kept in context. — [QwenLM/Qwen3 discussion #1398](https://github.com/QwenLM/Qwen3/discussions/1398)

### Inferences
- **Steady trajectories are one user message followed by up to 8 tool rounds.** Under the official template, the "keep thinking after the last user message" rule means all in-task thinking stays in context during rollout. Training should therefore see exactly the token stream vLLM saw. The safest approach is to store vLLM's prompt and completion token IDs and logprobs per turn and concatenate them, never re-render text through `apply_chat_template`. This is what TRL's `rollout_func` contract (`prompt_ids`/`completion_ids`/`logprobs`) and verl's delta tokenization are for.
- **Thinking must stay on.** Do not use TRL's `enable_thinking=False` examples. The Thinking-2507 template always opens `<think>` in the prompt, so the first generated token sequence starts inside the thinking block. Reward and format checks must expect output like `...</think>\n\n<tool_call>{...}</tool_call>`.
- **Loss mask** should be 1 for assistant-generated tokens (thinking, `<tool_call>` JSON, final answer, up to and including `<|im_end|>`) and 0 for system, user, `<tool_response>` and template-inserted tokens such as the auto `<think>`. This matches what `ai/notes/training.md` already does for SFT, so the same masking code can be reused.
- **Export:** the existing pipeline already serves a PEFT LoRA adapter (rank 16) with `vllm serve --enable-lora`. An RL-trained PEFT adapter in the same format drops in, provided `--max-lora-rank` is at least the adapter rank. For speed, LoRA serving is about 1.33–1.39x slower per token, so merging weights for production is an option once training is finished.
- **Version pinning:** TRL `environment_factory` needs transformers ≥5.2.0, and the project already pins ≥5.18.0. Pin a single tested trio of vLLM, TRL and PEFT (plus Unsloth, if used) on the pod, because the vLLM/transformers conflict means `pip install trl[vllm]` can silently downgrade or break one of them.

### Gaps
- No source specifically documented GRPO failures caused by Qwen3 thinking-history stripping. The risk is inferred from verl's and TRL's need to patch templates.
- Not verified: whether TRL PR #5390 (`tool_mask`) is merged in the current release, and whether TRL's `environment_factory` loop masks tool tokens by default. Check `trl/trainer/grpo_trainer.py` in the installed version.
- Not researched: specific vLLM version requirements for TRL 1.17 weight-transfer (`--weight-transfer-config`) and for Unsloth's fast_inference.
